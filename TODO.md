## Current shortcuts and technical debt

- [x] **P0 — Replace string-based HTTP error classification with typed domain errors.**
  A shared `DomainError` classification travels inside the `anyhow` chain, so the CLI still prints complete chains while `server.rs` selects each status and code by typed downcast instead of message text. Every public status/code mapping is covered by unit and HTTP tests.

- [x] **P0 — Redact internal error details in HTTP responses.**
  Every request carries a correlation ID returned as `X-Request-Id` and in the error envelope. Unexpected failures return a fixed generic message; expected client errors keep actionable wording that names records, views, and fields rather than filesystem paths or operating-system errors. JSON and HTML responses share the rules, and the complete chain reaches the server log under the request ID.

- [x] **P0 — Close production identity workflow gaps.**
  Owner delegation is first-class in the CLI and the local server, records both the effective principal and operator, and verifies the audited operator before revealing or trusting the target policy. The reserved user schema now has an open application-owned `profile` namespace while CR keeps identity, status, kind, and grants validated; bootstrap supports service owners; user definitions have atomic ensure/update and exact audited restore operations; global audit history is permission-filtered before its limit and always includes a principal's own policy history; blank agent session/turn values mean absence; audit attribution filters have unambiguous `--by-*` names with compatibility aliases; and `--json-errors` gives daemons stable error envelopes. Domain and CLI tests cover the boundaries, including concurrent ensure and direct-edit recovery.

- [x] **P0 — Harden every parent path against symlink escapes.**
  Every database-relative path is walked component by component from a descriptor for the resolved root, with `openat` and `O_NOFOLLOW`, and the target is opened, replaced, linked, renamed, or unlinked through its verified parent's descriptor. That covers `data_dir` and its intermediate directories, collection directories, record files, `.cr/`, and the audit, schema, view, and sync trees, on reads as well as mutations. Refusals are classified `DomainError::Conflict` and name the record, collection, or view rather than a path. `tests/symlink_escape.rs` constructs each escape and asserts nothing outside the root is read or written; nine of its eleven tests fail against the previous implementation, two of them by disclosing file contents from outside the database.

- [ ] **P0 — Add authenticated actor identity for stronger audit attribution.**
  CLI actors, `X-CR-Actor`, and bearer tokens are assertions, not authenticated people. Define a trusted identity integration or signed-request mode and distinguish authenticated principals from display attribution in audit events.
  Partially addressed and deliberately left open. Optional `agent`, `authorization`, and `intent` objects make delegated attribution expressible, and RBAC now normalizes the local actor to a stable principal, rejects a different `--actor` once access is enabled, evaluates that principal's fixed-schema `users` record, and stores the effective principal and policy hash in each allowed mutation's `access` object. That closes identity *consistency* inside one CLI process, not authentication: the process still controls `CR_ACTOR` and the backing files. `cr serve` now offers a loopback-only owner perspective console whose cookie selects an explicitly impersonated user; this is an administrative policy preview, and records the operator as `access.impersonated_by`, but deliberately is not a login system.
  **Principal tokens are the first authenticated identity.** `cr access token issue|list|revoke` (owner-only) keeps a SHA-256 verifier, ID, label, and expiry per token in a CR-owned `tokens` field of the user record, so issuing and revoking are audited policy versions and generic updates cannot write the field. `Database::authenticate_token` finds the token in the replayed policy, compares in constant time, checks expiry and status, and requires the user file to match its audited state, so a verifier planted by a direct edit authenticates nothing. `cr serve` accepts `Authorization: Bearer crt_…` beside its console, refuses a failing token with `401` rather than falling back to the owner, ignores the perspective cookie for it, and records `access.authentication: {method: token, credential: <id>}` on every event it writes — the distinction between an authenticated principal and display attribution this entry asked for, absent from every earlier event so their bytes are unchanged. `--require-token` removes the console, may bind beyond loopback, need not be launched by an owner, refuses `CR_API_TOKEN`, and warns when the database directory is open to other accounts; the file browser and pins stay console-only for every token. `tests/token_cli.rs` and `tests/token_http.rs` cover issue, refusal, revocation, expiry, drift, planted verifiers, and the server modes.
  **Cloudflare Access is the second, for people.** `cr serve --cloudflare-access <team> --cloudflare-access-aud <tag>` verifies the RS256 `Cf-Access-Jwt-Assertion` against the team's fetched and cached keys (refetched for an unknown `kid`, at most every ten seconds), checks `iss`, `aud`, `exp`, and `nbf`, and signs the request in as the one active user whose `email` matches the signed email, ignoring ASCII case; none, several, an inactive match, or no email (a service token) is `401`, and unfetchable keys are `503`. Unsigned `Cf-Access-Authenticated-User-Email` and `CF_Authorization` are never read. Events record `access.authentication: {method: cloudflare-access, credential: <sub>}`. It removes the console like `--require-token`, combines with it so scripts keep their principal tokens, gives each principal its own form token, refuses cross-site writes by `Sec-Fetch-Site` or `Origin`, and reports its keys in `/ready`. `tests/cloudflare_access_http.rs` signs real assertions against a loopback key server.
  What remains is the rest of the managed boundary: authenticate local callers by operating-system account over a Unix socket (`SO_PEERCRED`/`getpeereid`, a `peer` method beside `token`) so a daemon can own the directory without handing out secrets; make the CLI a client of that daemon (`CR_SERVER`/`--server`) so the account that owns the files is the only thing that opens them; self-service token rotation over the API; and, if a caller cannot keep a bearer secret, signed requests. Browser logins without an identity-aware proxy are the separate "browser sessions" entry below, which can exchange a principal token for its session.

- [x] **P1 — Support private and shared records in one RBAC collection.**
  The `x-cr-access` JSON Schema extension opts an empty, history-free collection into creator-owned records. Every creation path atomically stores the active principal as owner with private visibility; collection editors retain discovery and create rights without inheriting content access. Record owners can publish read-only access to the active-principal audience, make the record private again, transfer ownership, or use ordinary direct record grants for narrower collaboration. Reserved `$cr_access` metadata is plaintext, schema-excluded, generic-mutation protected, and included in ordinary record audit diffs. Access decisions bind its hash independently from the user's policy hash, and list, search, raw reads, relations, views, HTTP, and audit filtering use the same fail-closed evaluator. Existing collections keep legacy inheritance unchanged, and activation refuses existing records or history so no migration can publish a partially owned collection.
  The policy hides contents, not IDs. A record that does not exist answers `not_found` to every active principal, and only an existing record the principal cannot use answers `forbidden`, so a mistyped ID is not mistaken for somebody else's record; creating a taken ID already confirmed existence with `already_exists`. Record audit history keeps `forbidden` because it outlives the file. `tests/access_cli.rs` and `tests/access_http.rs` cover both answers.

- [x] **P1 — Verify a previewed change set against what was applied.**
  `--preview` on `create`, `update`, `link`, `delete`, and `save`, and `preview=true` on the equivalent REST routes, compute a change set and its digest without writing a record, an audit event, or a pending mutation, and without holding the audit lock afterwards. `--approved-changes sha256:…` and `X-CR-Approved-Changes` record the digest in `authorization.approved_changes` and bind the write to it: `cr` recomputes the digest from the change set it is about to record and refuses the mutation on a mismatch, and `audit verify` recomputes it from the stored `changes` and fails with `DomainError::ApprovalMismatch` / `409 approval_mismatch`, distinct from every other conflict so an auditor can tell an unapproved change from a corrupt chain. The canonical form is the exact byte range `changes` occupies inside the serialized payload, read with `RawValue`, so preview, apply, and verify share one definition and none of them depends on reserializing parsed values. `tests/fixtures/mismatched-approval` is a committed journal whose chain verifies and whose approval does not.
  Honest scope, because the field name invites more than it delivers: the digest commits to the change set and to nothing else — not to the rest of the event, not to the record's untouched fields, and not to a human having seen the preview, which an agent can assert by computing the digest itself. Its value to an auditor is as something to compare against an approval recorded elsewhere. The `before_hash` guard does *not* combine with it to give "the human approved exactly this": a competing `cr update` moves the record and the audited state together and passes that guard, and it is the digest, not `before_hash`, that notices. Approving a multi-record `save` is refused rather than checked against one of several change sets; that needs a per-record mapping and waits on the bulk-mutation entry above.

- [x] **P2 — Make attribution enum growth safe.**

- [x] **P3 — Populate attribution from agent harnesses instead of flags.**
  A Claude Code `PreToolUse` hook cannot set the environment of the command it precedes: only `SessionStart`, `Setup`, `CwdChanged`, and `FileChanged` hooks get `CLAUDE_ENV_FILE`, and none of them runs per call. It can replace the tool input through `hookSpecificOutput.updatedInput`, so `examples/hooks/claude-code-attribution.sh` (POSIX `sh` and `jq`) prepends one `export` line to Bash commands that run `cr`, copying every other input field through. The line carries `CR_HOOK_AGENT` (`claude-code`, `session_id`, and `prompt_id` as the turn) and `CR_HOOK_AUTHORIZATION` (`permission_mode` verbatim as the grant; `auto`, `dontAsk`, and `bypassPermissions` map to `delegated` and everything else to `unknown`, never `interactive` or `autonomous`, because the hook runs before the permission check and a mode says nothing about who is present). The hook makes no permission decision, never exits 2, drops a value `cr` would reject instead of failing the write, and as a `SessionStart` hook appends the session alone to `CLAUDE_ENV_FILE`. The variables are a channel of their own rather than `CR_AGENT`, which would have been recorded as `flag` like a model's declaration and would have overridden a user's own `CR_AGENT=none`. They are recorded as the new `detected_from: hook`, added through `stored_label_enum!` so a build without it verifies, displays, and appends after a hook event (checked against a pre-change binary), with no existing byte changed. The layer sits above the probe and below every declaration: a declared agent, `none` included, drops the agent and its grant together, and declaring any agent or authorization detail over it records the declaring source, so `hook` never credits the hook with a grant the caller chose. `docs/agents.md` documents the hook, the mapping, and the limits that remain in Claude Code's contract: permission rules see the rewritten command, so the export line is a subcommand `Bash(cr *)` does not cover and can add a prompt (or a `dontAsk` refusal, where the session-start form alone is the answer), and sub-agents are recorded as their parent session. It also documents the Git convention: the human as author and `cr` actor, the agent as committer through Claude Code's settings `env`, `Co-authored-by:`, and a `Cr-Audit-Head:` trailer from `examples/hooks/commit-msg`. `tests/example_hooks.rs` runs both hooks on documented payloads, through the shell and `cr` to a verified audit event, and through real `git commit` and `--amend` calls.

- [x] **P1 — Add conditional writes and optimistic concurrency.**
  The version of a record is `sha256:` plus SHA-256 over `b"cr:record:v1\0" || exact_stored_markdown_bytes`; retaining that domain prefix preserves the hashes already stored in audit history. Domain and JSON records expose it; REST single-record and exact-document reads return the quoted form as a strong `ETag`. `If-Match` is optional for atomic `PATCH`, delete, and link mutations, while whole-document `PUT` requires it (`428 precondition_required` when absent); stale or weak validators fail as typed `412 precondition_failed` responses. Server-rendered edit and delete forms carry the version automatically. CLI `update`, `link`, and `delete` accept `--expected-record-hash`, and `cr get --json` supplies the value. Every comparison occurs after acquiring the audit lock and before preparing or committing the audit event, so a failed condition writes neither record nor history and cannot race the mutation. Sync captures every target version under that lock at the pre-application audit head, persists the snapshot for recovery, and combines conditional target writes with an audit-sequence precondition advanced by its own events. That extra generation guard rejects intervening writers even when an edit restores byte-identical contents; recovery captures history under the same lock, trusts only source-marked run events whose action and resulting hash match the stream, and reconstructs the target snapshot for legacy version-1 ledgers from their recorded audit prefix. Preview and approved-change digests remain orthogonal: a conditional preview checks the version, and an approved apply still verifies its canonical change set.

- [x] **P2 — Make health checks reflect database readiness.**
  `GET /ready` sits beside `/health`, which stays the liveness probe, and answers `200 {"status":"ready"}` or `503` listing every check that ran as `{name, ok, code}` with the request ID. It is public like `/health`, because a probe cannot attach a bearer token, so names and codes are a fixed vocabulary that never carries a path, record, sync name, or count, and each failure's reason goes to the `cr error` log line under the request ID. The checks in `src/readiness.rs` are cheap and never wait: `database` opens the root, `.cr/`, and the records directory through the symlink-safe walk, and is the only check listed when it fails; `config` reloads `.cr/config.yaml` through the function `Database::discover` uses; `audit_recovery` and `sync_recovery` report a pending mutation or a sync run ledger only when the lock that owns it is free when tried without waiting — the audit lock, and the sync application lock rather than the per-sync lock that `cr sync run` refuses on — so a write or an import in progress is not a failure; and `journal` compares the head of the server's `JournalCache` walk with the last event of the newest segment, answering `journal_warming` until the walk `cr serve` starts on listening returns, `journal_unverified` after a walk failed, `journal_changed` when the disk is behind or differs at the head, and `journal_unreadable`. A probe recovers nothing, creates nothing, and never walks from the first event, so a forgery below the head stays the next read's to find, and a load balancer that withdraws traffic leaves the condition to the command the log names or a restart. The route is in OpenAPI, `ready` is a reserved view name, and `docs/http-api.md`, `docs/web-ui.md`, and `docs/architecture.md` document the codes and the reasoning.
  `tests/readiness_http.rs` covers a healthy database (warming, then ready, public under `CR_API_TOKEN`); a mutation interrupted by `tests/common/fault.rs` (not ready, ready while the audit lock is held, recovered by the next journal read); four configurations `cr` cannot load; a sync run stopped partway (not ready, ready while the application lock is held, cleared by `cr sync recover`); a journal that lost its head, a damaged newest event, and a failed walk; and a moved `.cr/`. Every `503` is checked to carry only names, codes, and the request ID. `tests/server_network.rs` brings a real `cr serve` to ready and finds the reason in its log.

- [x] **P2 — Handle service shutdown signals consistently.**
  `cr serve` registers `SIGINT` and `SIGTERM` before it binds and treats them alike: the first closes the listener and idle connections, drains every accepted request with no timer of its own, and exits 0; a second stops waiting, abandons those responses, and exits 1. Neither interrupts database work, because the runtime is dropped rather than timed out: a mutation that has started commits before the process exits, and one that has not never starts. `SIGHUP` keeps its default action on purpose, since catching it would override `nohup`, and off Unix only Ctrl-C is handled, as before. `docs/web-ui.md` documents the behavior and `docs/architecture.md` the reasoning.
  `tests/server_shutdown.rs` runs a real server and catches a request in flight with `Expect: 100-continue`, so every step is ordered rather than timed: either signal drains and exits 0 with an idle keep-alive connection open; `SIGTERM` with a create in flight refuses new connections, answers it `201`, and exits 0 over a chain that verifies; a second signal exits 1 having written nothing; on Linux, a create already waiting for the audit lock, observed in `/proc/locks`, still commits after a second signal; and a mutation the server left half done, its append blocked as in `tests/audit_fault_injection.rs`, is recovered when the server restarts. A `SIGKILL` inside the mutation window itself stays under crash/fault injection below.

- [x] **P1 — Declare a content security policy.**
  Every HTML answer — documents, fragments, refused forms, the error page — carries `Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, set in `html_response`. `default-src 'self'` is the fallback for every fetch and grants neither `'unsafe-inline'` nor `'unsafe-eval'`; the other four are what it does not cover or would allow: no plugins, no `<base>`, no form submitting to another origin, and no framing. Browsers apply `form-action` to a submission's redirects too, so behind an authenticating proxy a native form submitted after the session expired is refused rather than sent to the sign-in page, which the next link reaches as before; `docs/web-ui.md` says so. There are no nonces or hashes because nothing inline needs one, no `upgrade-insecure-requests` because `cr serve` speaks plain HTTP, and no reporting endpoint.
  The three obstacles went as this entry proposed. `GLOBAL_STYLES` is now `src/static/cr.css`, served as `/static/cr-<digest>.css` and linked after the utilities, which it still beats by being unlayered rather than by order; Tailwind no longer scans that CSS as if it were markup, so six utilities nothing used dropped out of `tailwind.css`. The favicon is `/static/favicon-<digest>.svg` rather than a `data:` URL, so images need nothing beyond `'self'`. The perspective selector's `onchange` was removed rather than moved into `cr.js`, because submitting on change was the WCAG 3.2.2 defect itself: the select changes nothing until **Switch** is pressed, a button everyone now gets rather than a `<noscript>` fallback, and the form stays unboosted because its `303` would otherwise push `/perspective` into the address bar. `cr.js` already switched off htmx's injected indicator `<style>` and now also sets `allowEval = false`, so a trigger filter or `hx-on` added later fails with htmx's own error rather than a policy refusal. `tests/csp_http.rs` asserts the exact policy on every kind of HTML answer with access control off and on, and reads every tag of every page, with markup written into a record, a view title and a browsed file: it fails on a `<style>` element, a `style` attribute, an `on*` or `hx-on` attribute, a `<script>` without a `src`, a `javascript:` or `data:` URL, `<base>`, plugins, frames, a trigger filter or `js:` value, and any stylesheet, script, icon, form action or htmx request on another origin, then fetches every asset the pages link. In headless Chrome a load, a boosted navigation, a targeted re-sort and a perspective switch raise no `securitypolicyviolation`.

- [x] **P3 — Send `nosniff` on every response, not only HTML.**
  The content security policy's `'self'` trusts every URL on the origin as a script or stylesheet source, not only `/static/`, and `X-Content-Type-Options: nosniff` is what makes a browser refuse a response in either role whose type is not JavaScript or CSS. `request_context`, the outermost request layer and the one that stamps `X-Request-Id`, now inserts it once on every response, so the JSON API and its errors, `/health`, `/openapi.json`, `/static/*`, redirects, and the `404` and `405` fallbacks carry it as well as the pages. `html_response` no longer sets its own, and `insert` rather than `append` keeps a handler that did from sending two. The policy itself, `frame-ancestors` included, is still HTML-only. `tests/csp_http.rs` walks a JSON success, a handler's `404`, the fallback's `404`, the asset route's refusal, `/health`, `/openapi.json`, a page, the HTML error page, a fragment, every asset the home page links, a `405`, a form's `303`, and the `401` that `CR_API_TOKEN` gives the API, the OpenAPI document and a page, and asserts exactly one `nosniff` on each. `docs/http-api.md`, `docs/web-ui.md` and `docs/architecture.md` say so.

- [x] **P2 — Preserve submitted form values on validation errors.**
  A refused create or update is answered with the form instead of the generic error page: every value comes back in the control it was typed into as the exact submitted text, escaped — including the additional-attributes YAML, the raw front matter, and the Markdown body — rather than a reparsed round trip that would normalize `12500.50` to `12500.5` and reorder a mapping's keys. `Database::schema_violations` reports each schema failure with the dotted front matter path the schema locates it in, the same derivation `cr check` records in a finding's `field`, and the form renders each beside that control and marks it `aria-invalid`; a violation the schema locates in the record as a whole stays a form-level message rather than being guessed onto a field. - [x] **P3 — Give the save-as-view form the refused-form treatment.**
  A refused save answers with the form instead of the generic error page, under the status of the refusal: a name already taken is `409`, an empty one `400`, one no view may have (a path separator, `.`, a reserved route) `422`, and a Kanban layout with nothing to group by `422`. - [x] **P1 — Classify the remaining CLI-only failures.**
  `sync.rs`, `Database::init`, and `Database::discover` attach a `DomainError` to every failure a caller can act on, so `--json-errors` gives an unattended job a code to branch on rather than `internal_error`, and a future route inherits the status. A database that is not there — a missing `--database` path, a directory without `.cr`, no `.cr` above the working directory — is `not_found`; `init` over an existing one is `already_exists`; an unusable `config.yaml` (YAML, format version, `data_dir`, a zero audit bound) is `validation_failed`, as a malformed schema or view is. An unknown sync is `not_found` and a taken name `already_exists`. A definition that cannot run and adapter output the protocol refuses — non-UTF-8, a malformed line, a duplicate target, a checkpoint that is not last, too many messages — are `validation_failed`, the same answer a schema violation in that output already got. State is `conflict`: the audit head, a target record, or the checkpoint changing while the adapter ran; another run holding the sync lock, and only `WouldBlock`, since failing to take the lock at all is the operating system's problem; a checkpoint or run ledger that no longer parses; and a file in `.cr/syncs` whose name cannot be a sync, refused by filename the way an unusable record filename is. The adapter *process* needed a new variant, `DomainError::AdapterFailed` / `adapter_failed`: a program that is missing or not executable, a nonzero exit, a timeout, or an output-limit breach is not the caller's request, not database state, and not a defect in `cr`, and a scheduler has to tell "retry later" apart from all three. HTTP maps it to `502`, whose body carries the generic message like every `5xx`. Classified messages name the sync or say "a database", never a path; the root, the configuration file, and the adapter program stay in the chain beneath them. Left unclassified on purpose: operating-system failures creating or resolving the root, reading the working directory, staging state input, locking, spawning for any other reason, and reading adapter output, plus serialization and run-ID generation. - [x] **P3 — Classify the CLI's own argument refusals.**

- [x] **P3 — Reach or remove the unreachable `invalid_location` error.**
  It was unreachable, so it is gone. `HeaderValue::from_str` refuses only control characters other than tab and `DEL`, and every redirect target — the `303` `Location` of `see_other`, the `HX-Location` of `mutation_redirect`, and the `Location` of a record created over the API — was built from literals, the `&'static str` panel anchors, segments escaped by `encode_segment` (whose set starts from `CONTROLS`, and which escapes every non-ASCII byte), and queries from `form_urlencoded`, which leaves nothing but ASCII alphanumerics and `*-._+=&%`. A view name, record ID, notice naming a record's title, or browse path containing CR or LF therefore never reached the header raw. Rather than leave that a property of every caller, all three now build the header through `location_header`, which percent-escapes control characters, spaces and non-ASCII bytes and leaves `%` and the rest of URL syntax alone: it is the identity on every URL the routes build, so no escape is escaped twice, and what it returns is visible ASCII by construction, which its one `expect` states. `see_other` and `mutation_redirect` return `Response` instead of `ApiResult<Response>`, so the type says a redirect cannot fail, and the `invalid_location` code, which no guide or OpenAPI schema listed, no longer exists. `server::tests::every_redirect_target_becomes_a_header_that_cannot_split_the_response` checks that the URL builders pass through unchanged on an input holding a space, `%`, `?`, `#`, `/`, Unicode, tab, NUL, `DEL`, CR and LF; that `\r\nSet-Cookie:` stays inside the `Location` of a `303` and the `HX-Location` of a `204`; and that every Unicode scalar value at once comes out as visible ASCII.

- [x] **P2 — Move the crate to edition 2024.**
  `edition = "2024"`, with `rust-version` left at 1.89: edition 2024 needs 1.85 and the let-chains it enables need 1.88, so neither sets the floor. `cargo fix --edition` found nothing to change, and neither did any migration lint named individually (`if_let_rescope`, `tail_expr_drop_order`, `impl_trait_overcaptures`, `static_mut_refs`, `unsafe_attr_outside_unsafe`, `missing_unsafe_on_extern`, `keyword_idents_2024`, `rust_2024_prelude_collisions`, and the rest of `rust_2024_compatibility`), across lib, binary, and every integration test. The tree had nothing for them to catch: no `unsafe fn`, no `extern` block, no `static mut`, no `gen` identifier, no `macro_rules!` taking an `expr` fragment, and the one RPIT signature (`database::update_with`) already writes the `+ 'a` bound that edition 2024 would otherwise change the meaning of.
  The two silent traps do not apply either. Every audit and sync lock is a named `File` local (`let _lock = audit.lock()?`), never a temporary in an `if let` scrutinee, so `if let` rescoping cannot shorten one; and no tail expression builds a temporary with a significant `Drop` beside such a local, so tail-expression drop order cannot reorder one.
  What the migration did cost is real but mechanical: rustfmt's 2024 style edition reordered imports and rewrapped call chains across 30 files, adding a trailing `;` to six `return Err(...)` match arms, and let-chain stabilisation made `clippy::collapsible_if` fire on seven nested `if let`s, which are now `&&` chains. Comparing the non-whitespace character multiset of every touched file before and after shows exactly those two changes and nothing else.

## Query and result capabilities

- [x] **P1 — Comparison expressions.**
  Support typed numeric, string, and date comparisons such as `value > 10000`, `score >= 80`, and `expected_close < 2027-12-31`.

- [x] **P1 — Boolean expressions.**
  `--filter` on `list`, `search`, and `backlinks`, and `filter` on the equivalent HTTP routes, take one expression with `AND`, `OR`, `NOT`, and parentheses, where `NOT` binds tighter than `AND` and `AND` tighter than `OR`. `src/query.rs` holds the only tokenizer, parser, and evaluator, so the CLI and HTTP cannot disagree, and every comparison delegates to the same `operator_matches` that `--where-expr` and saved views use. Parse errors name what was expected and the one-based column, including the common case of an unquoted value with a space in it. Saved views still store their AND/OR filter groups rather than a `filter` string; letting a view carry one is a small follow-up.

- [x] **P1 — Membership, containment, and existence operators.**
  The filter language adds `in [...]`, `not in [...]`, `exists`, `not exists`, `is null`, and `is not null` beside `contains`, `not-contains`, `starts-with`, `ends-with`, and the emptiness tests, and matches `$id`, `$collection`, and `$path`. Missing, `null`, `""`, `[]`, and `{}` are distinguishable: `exists` is presence, `is null` is presence with a null value, exact equality tells the empties apart, and `is-empty` covers all of them. Every other test is false for a missing field. Quoted values are always strings and bare values are YAML scalars, exactly as `--where` reads them.

- [x] **P1 — Sorting.**
  `--sort` on `list`, `search`, and `backlinks`, `sort` on the equivalent HTTP routes, and a saved view's default order take up to five ordered keys written `FIELD`, `FIELD:asc`, or `FIELD:desc`, comma-separated or repeated. Each key applies the single-field rules — typed YAML ordering, missing values last in either direction — to what the keys before it leave tied, collection and then record ID break whatever every key leaves tied, and all of it happens before pagination. A suffix was chosen over JSON:API's `-FIELD` because clap reads `--sort -value` as a flag and accepting leading hyphens would let `--sort --json` sort by a field named `--json`; the suffix is the same text in a shell, a URL, and a view file. `-FIELD` is refused with the spelling that works, and only a final `:asc` or `:desc` is a direction, so `og:title` stays a field. `--desc`, `direction`, and `cr view create --sort-direction` keep working for one key written without a direction and are refused with more, rather than guessing whether they mean the first key or every key; more than five keys and a repeated field are `validation_failed`, which on the command line is the code every value the database parses from text keeps. A one-key view is still written as `sort_by` and `sort_direction`, so older files load, render, and save unchanged, and several keys are a `sort` list, never beside `sort_by`; `cr view show --json` gives `sort` plus the first key as `sort_by` and `sort_direction`. The HTML query carries a sort as `sort_field`/`sort_direction` pairs matched by position, like the filter triples, so one-key URLs are unchanged. The filter panel and the view editor render a **Then by** row per further key plus one empty row, so keys are added and removed without JavaScript; a column heading replaces the whole sort with its column; and pagination, targeted swaps, **Edit view**, and **Save as view**, including the form a refused save answers with, keep every key in order. The panel keeps the first of a field chosen twice rather than fail a swap, where the CLI, REST, the editor, and view files refuse it. `src/sort.rs` is the one implementation, unit-tested there and in `src/views.rs`, and `tests/sort_cli.rs`, `tests/server_api.rs`, `tests/views_cli.rs`, and `tests/views_http.rs` cover the surfaces. A field whose name contains a comma cannot be a sort key.

- [x] **P1 — Field projections.**
  `--select` on `get`, `list`, `search`, `backlinks`, and `traverse`, and `select` on the equivalent HTTP routes, take comma-separated or repeated selectors: dotted front matter paths and `$id`, `$collection`, `$path`, `$version`, and `$body`. A projected record is a flat object keyed by the selectors as written, leaving out fields the record does not have, or in plain CLI output one tab-separated row with escaped tabs, newlines, carriage returns, and backslashes. `traverse` puts the projection under `fields` in place of path, version, and front matter, and a projected single record keeps its `ETag`. `src/projection.rs` is the one implementation. Projected results are still computed from fully read records; the index entry above is what would avoid reading unselected fields. `tests/select_cli.rs` and `tests/server_api.rs` cover it.

- [x] **P1 — Counts and aggregation.**
  `cr count COLLECTION` and `GET /api/v1/collections/{collection}/count` count the records `list` would return under the same `where`, `where_expr`, and `filter`. `--by`/`by` counts once per distinct value, in sort order with records missing the field last (`missing: true` in JSON), which is also how distinct values are listed; `--sum` and `--avg` summarize numeric values only, with exact integer sums; and `--min` and `--max` take any present, non-null value in sort order, so they work on ISO dates. Output is a tab-separated table with a header, or JSON; no body is ever returned. `src/aggregate.rs` is the one implementation. Two things are deliberately left out: grouping by each element of a list field (such as counting by tag) rather than by the whole list, and grouping by more than one field. Like `list`, counting reads every matching record.

- [ ] **P2 — Additional streaming output formats.**
  Add JSON Lines and CSV where the projection is tabular. Large results should stream rather than building the complete response in memory.

- [x] **P2 — Saved and reusable filtered queries.**
  Versioned `.cr/views/*.yaml` definitions provide named collection queries, typed equality filters, shared comparison/containment/empty expressions, dotted columns, default ordering, and page sizes to CLI discovery and server-rendered routes.

- [ ] **P2 — Query planner and disposable indexes.**

## Relationships

- [x] **P1 — Add `unlink` and its REST equivalent.**
  `cr unlink` and `DELETE /api/v1/collections/{collection}/records/{id}/links/{relation}/{target_collection}/{target_id}` remove every reference to one record from a named relation, matched by `collection` and `id` so an annotated or duplicated reference goes too, and prune the relation and then `relations` once empty, so link-then-unlink restores the record byte for byte. Removing an absent reference succeeds and changes nothing, as a repeated link does. The target is never read, so a dangling reference can be removed and only link permission on the source is needed. The write takes the ordinary single-record path, so it is schema-validated, atomic, previewable, approvable, conditional on `If-Match` or `--expected-record-hash`, and retryable with an idempotency key. It is recorded as a `link` event whose change set shows the removal, rather than as a new `unlink` action that every earlier `cr` would refuse; its retry key is scoped to `link` with the request marked as an unlink, for the same reason. `tests/relations_cli.rs` and `tests/server_api.rs` cover it. The record page's relations panel has a **Remove** control that performs the same operation.

- [x] **P1 — Backlink queries.**
  `cr backlinks COLLECTION ID` and `GET /api/v1/collections/{collection}/records/{id}/backlinks` list every readable record whose relations refer to a record, each with the names of the relations holding the reference. `--from`/`from` limits the source collection, `--relation`/`relation` the relation, and the ordinary `where`, `where_expr`, `sort`, and `direction` apply to the source records; HTTP paginates like any list. A reference is matched by `collection` and `id` exactly as `unlink` matches it, a malformed `relations` value refers to nothing (`cr check` reports it), and the target is never read, so references to a deleted record are found and nothing about a target the caller cannot read is disclosed. Like `list`, it scans every source record; the disposable-index entry above is what would make it cheap. `tests/backlinks_cli.rs` and `tests/server_api.rs` cover it.

- [x] **P2 — Show relations and backlinks on the record page.**
  The record page lists what a record links to, by name and linked to the other record's page, and what links to it, with the same readability rules as `cr backlinks`: a missing or unreadable record is shown only by the `collection/id` the relation states. **+ Link a record** and **Remove** run `link` and `unlink` with the page's version as their precondition, suggesting relation names and records already in the database. The record form carries the stored `relations` through as a hidden value, so a save can neither retype nor undo them, and the version makes a save after a concurrent link fail with `412`. What remains: the panel reads every readable record once per record page, the scan `cr backlinks` makes; the disposable index above is what would bound it. A new record's relations are still typed as YAML, because there is no record to link from until it exists. `tests/record_relations_http.rs` covers it.

- [x] **P1 — Relationship traversal and expansion.**
  `cr traverse COLLECTION ID` and `GET /api/v1/collections/{collection}/records/{id}/traverse` follow relations outward breadth first, limited to repeatable `--relation`/`relation` names at every step, for an explicit `--depth` from 1 (the default) to 10, and at most 1,000 records, beyond which the result says `truncated`. Each record is visited once, so a cycle ends where it closes. Every record after the start is read with `get`'s authorization, and a reference that cannot be followed becomes a node with status `missing`, `forbidden`, or `unreadable` rather than an error; only the start must exist. Output is a plain indented tree, a flat JSON graph of nodes and edges, or with `--expand`/`expand=true` a nested tree that expands each record where it was first reached and stubs every later reference as `seen`. Reads share one lazily loaded audit replay. Field projections are the separate entry below, and will apply here too. `tests/traverse_cli.rs` and `tests/server_api.rs` cover it.

- [x] **P1 — Whole-database integrity checks.**
  `cr check` and `GET /api/v1/check` report twelve finding kinds without stopping at the first one: dangling links, malformed relation values, schema violations, unusable collection schemas, invalid record and collection names, records that cannot be read or parsed, the three audit reconciliation states (no history, audited file missing, content divergence), a journal that cannot be replayed, a stored change set that does not match its approval, and a sync run that stopped partway. Findings name records by `collection/id` and never by path, and `src/check.rs` holds the logic so `database.rs`, `main.rs`, and `server.rs` only gained seams. Exit status is 0 for clean, 2 for "ran and found problems", and 1 for "could not run"; `--fail-on error|warning|never` moves the threshold and `--collection` bounds the expensive phase. `check` is strictly read-only, proven by a byte-level before/after snapshot over the whole database in `tests/check_cli.rs` and `tests/check_http.rs`.
  Three deliberate boundaries. `cr status` keeps the working-tree view, so a divergence `cr save` could reconcile is reported at `warning` and points back at `status`; the same divergence becomes an `error` when the record also fails to parse or validate, because then `save` refuses it and nothing but `check` explains why. The interrupted-sync-run finding is a durability report rather than an integrity one — the run ledger is not hash-chained, the committed prefix genuinely agrees with the journal, and `check` does not take the per-sync lock so it cannot tell an abandoned run from one in flight — so it is a `warning` that names the sync and points at `cr sync recover <name> --check`. And `check` never repairs, including never completing a sync run it just reported; see the `--fix` entry below.

- [ ] **P2 — Decide whether `cr check --fix` should exist.**
  `check` is deliberately read-only: the findings it reports have genuinely different right answers (a dangling link may want the relation removed, the target restored, or a delete policy applied), and a command that both diagnoses and mutates cannot be run unattended from cron. If a repair mode is ever added it must be a separate verb rather than a flag on `check`, must require naming what to repair, must write ordinary audited events rather than editing the journal, and must not be able to resolve a finding by deleting data. The `unlink`, delete-policy, and relationship-constraint entries above are prerequisites for most of what a fix would want to do.

- [ ] **P2 — Give `check` an incremental or bounded mode.**
  `check` reads and parses every in-scope record and replays the journal twice — once for record state and once for the approval digests — so it is O(records + 2·events) with no index, exactly like `list` and `search`. It also holds the audit lock for the whole scan, as `status` does, so a check over a large database blocks writers for its duration. `--collection` is the only bound today. The disposable-index entry above would fix the record half; a cached replay to a known-good head would fix the journal half.

- [x] **P1 — Have `check` judge record access metadata the way writes do.**

- [ ] **P1 — Encrypted bundle records.**

- [ ] **P2 — Stream large supporting files.**

- [ ] **P3 — Refuse supporting-file names a filesystem would normalize together.**

- [ ] **P3 — Record file modes of supporting files.**

## HTTP and integrations

- [ ] **P1 — Bulk mutation endpoints and multi-record transactions.**
  Define atomicity, validation, audit grouping, crash recovery, maximum batch sizes, and partial-failure behavior before exposing bulk create/update/delete. Deliberately still open: nothing here is a multi-record transaction.
  The sync half of it is closed to the strongest property available without one. Sync runs still preflight their bounded stream and commit sequential single-record mutations, so a durable application failure still commits a prefix — but it can no longer do so silently. A run ledger and the run's exact validated stream become durable under `.cr/sync/runs/` before the first mutation and are removed only once the checkpoint agrees with the committed work, so an interrupted run is a fact on disk rather than an inference. `cr sync run` refuses to start over one, and `cr sync recover <name>` completes it by replaying the recorded stream forward — sound because the protocol stream is idempotent by construction — under the interrupted run's own ID; `--check` reports it while reading committed progress back out of the audit chain rather than keeping a second copy. Rollback is not attempted and is not wanted: the journal is append-only, and appending inverse mutations would trade a true history for a longer one that gains nothing over finishing the run. Per-record checkpoint advancement is impossible by protocol, because the adapter emits one opaque cursor at the end.
  What remains for this entry: genuine all-or-nothing application across several records, which needs a staging-and-publish design for record files plus an audit protocol that can commit a group of events as one unit; bulk create/update/delete over HTTP and the CLI built on that; and per-record approval mapping so `--approved-changes` can cover a multi-record `save`. Recovery of a run whose original failure persists remains a truthful stuck state that needs a person, and a replay can re-drive an adapter's remote side effects, which is the neighbouring "remote-effect idempotency" entry.

- [x] **P1 — Idempotency keys for retried mutations.**
  CLI create/update/link/delete and REST record POST/PATCH/PUT/DELETE/link POST accept bounded, high-entropy retry keys. The raw key is never persisted: a principal/operation/record-scoped key hash, HMAC-SHA-256 of the lossless typed-YAML plaintext request keyed by the raw retry key, and original result are committed inside the same audit event and pending-mutation protocol as the write. Exact retries re-run current authorization and return that result without another event; protected results retain exact ciphertext Markdown/version durably and decrypt only for the response, while the stored safe relative path keeps replay stable across `data_dir` changes. Mismatched reuse is typed `idempotency_conflict`; concurrent callers serialize under the audit lock; pending recovery closes both response-loss crash windows; previews and failures consume nothing. The scoped identity occurs at most once regardless of request hash, enforced by replay, lookup, preparation, append, and recovery as typed `audit_integrity_failed`, while a pending copy of its already-committed event remains an honest cleanup case. Verification binds the stored result back to the replayed ciphertext event state, exact bytes, before/after version, collection, and ID, including delete tombstones. V1 is honestly single-record: multi-record save and sync, managed user/access lifecycle commands, and HTML form posts remain outside this contract until they have command/group result semantics; sync explicitly clears a caller retry key and `user ensure` remains independently declarative.

- [x] **P1 — Authorization policies.**

List/search omit unreadable records; scoped history requires audit-read access; database-wide integrity operations require ownership; editors cannot delete; access managers cannot mint ownership or other access managers; and the last database owner cannot be removed. Owner-only user deletion records a full-state tombstone, supports complete-chain `--if-unused` checks, keeps historical actor references verifiable, and blocks ID reuse unless `--reuse-deleted-id` is explicit. CLI commands enforce the resolved local principal, while `cr serve` provides a loopback-only owner console that can explicitly impersonate each user and records the owner behind allowed impersonated mutations. ## Audit, security, and operations

- [ ] **P1 — Signed or remotely anchored audit checkpoints.**
  **Ed25519 signing is done; trusted timestamping and transparency-log publication are not.** While `CR_AUDIT_SIGNING_KEY` names a private key from `cr audit key generate` (created `0600`, never overwritten, public key printed alone on its last line, `cr audit key show` to print it again), the single `append` funnel writes `.cr-audit-head.sig.json` right after the anchor: `{version, database, sequence, hash, timestamp, key_id, signature}`, a self-contained Ed25519 signature (`ed25519-dalek` 3, `verify_strict`, builds on the 1.89 MSRV) over `cr:audit:checkpoint:v1\0` and length-prefixed database identity, sequence, event hash, and event timestamp. The identity is the journal's first event hash; `.cr/encryption.json`'s `id` was rejected as optional, editable in place, and outside the chain. A sibling file rather than anchor v2, because `load_anchor` refuses unknown versions and every earlier `cr` would have called a signed database `anchor_mismatch`; the anchor's bytes are unchanged. A crash between the two writes leaves the signature lagging, judged by position exactly as the anchor is. A write signs only when the stored checkpoint verifies under a key it trusts (its own plus `CR_AUDIT_TRUSTED_KEYS`) and agrees with the journal, or the journal is empty; a trusted checkpoint that disagrees refuses the write before the pending file, and a missing or untrusted one signs nothing, so automation never signs over a forged head or starts a signed history by itself. Adoption, re-signing, and rotation are `cr audit anchor --write`, which applies the same refusal. `cr audit verify --trusted-key KEY|FILE` (repeatable, else `CR_AUDIT_TRUSTED_KEYS`), `cr check --trusted-key`, and `trusted_key` on `GET /api/v1/audit/verify` and `/check` (inline keys only, server env as the default) judge it; without keys, verification is unchanged down to its response bytes and only notes that a checkpoint exists. Failures are the new `DomainError::SignatureMismatch` / `409 signature_mismatch`: missing, untrusted key, not verifying, another database, or disagreeing history. `check` adds `audit_signature_mismatch` and `audit_signature_missing` as errors and `audit_signature_behind` as a warning. `cr` warns about a key file inside the database, and `cr serve` refuses to start with an unusable key. `tests/audit_signing.rs` covers the round trip with an independent re-derivation of the signed message, an untrusted key, the forged-head-actor forgery with its anchor re-derived (refused by verify, check, the key holder's next write, and `anchor --write`, and not laundered by deleting the checkpoint), an edited checkpoint, a lag, a checkpoint copied from another database, unsigned databases, adoption, two signers, key permissions, and the REST routes; CI's `msrv` job builds it on 1.89.
  What remains: freshness. Truncating the journal and restoring an older signed checkpoint with it verifies; today only the Git history of the file and `--expected-head` catch that. RFC 3161 trusted timestamps over the checkpoint, or publishing it to a transparency log (and verifying inclusion and consistency), would. Also open: `cr status` still reads no anchor or signature, a key that signs several databases cannot tell a wholesale substitution of one by a copy of another, and SSH-format keys (`ssh-keygen -Y`, `allowed_signers`) are not accepted.

- [x] **P1 — Detect a forged newest record result without an external checkpoint.**
  `audit verify` now replays every record's change sets and requires each semantic post-state to reproduce that event's exact `after_hash`; the formerly ignored forged-head test is enabled. Version 3 events add a versioned exact-Markdown `after_snapshot` to every present post-state. Replay parses the witness back to the same semantic state before hashing its exact bytes, so YAML spelling is evidence rather than something a renderer guesses. Actions are bound to their presence transitions, and baseline is valid only as a record's first event.
  Version 1 and 2 events remain compatible without making a false byte-equivalence claim. A non-reproducible legacy event records a representation gap; a later strongly verified transition clears it. When the gap remains at a record head, only the materialized file with the exact stored hash can serve as its witness, and its parsed document must equal semantic replay. This covers old baselines, managed-user mapping order, and direct `save` events. Payload versions can increase but cannot decrease mid-journal; proving that the first event or the complete history was not rewritten from v3 to v2 still requires the signed or remote checkpoint above.
  Replay is also mutation admission: `prepare`, reconciled saves, sync recovery, and pending-mutation recovery all refuse an already inconsistent journal before creating a pending write or appending an innocent event. The failure is `DomainError::AuditIntegrity` / `409 audit_integrity_failed`, names the guilty sequence, and publishes no path or value. What remains is deliberately the signed/remote-checkpoint entry above: replay cannot derive actor, timestamp, message, authorization, intent, or attribution from record state, and an attacker who rewrites the newest event into an internally consistent different state can update its `after_hash`, the record, event hash, and local anchor together. `tests/audit_corruption.rs::a_forged_head_actor_still_needs_an_external_checkpoint` keeps that boundary executable.

- [x] **P1 — Anchor the audit head to a file the version control system carries.**
  `.cr-audit-head.json` sits at the database root, outside `.cr/`, and records `{version, sequence, hash, timestamp}` for the newest audit event — every field derived from the journal, the timestamp being the anchored event's own rather than the time of writing, so the file is a pure function of the chain and two databases holding the same journal hold byte-identical anchors. It is rewritten inside `AuditLog::append`, which is the single funnel for `create`, `update`, `link`, `delete`, `save`, `sync`, `audit baseline`, and pending-mutation recovery, so no path that advances the chain can leave it behind. `cr audit verify` checks it by default, `cr check` reports it, and `cr audit anchor [--write]` inspects and repairs it.
  Honest scope, because the location invites more than it delivers: a file at the database root is writable by anybody who can write `.cr/`, so on its own the anchor stops nothing — the forger re-hashes the event and rewrites the anchor in one pass. **The protection comes entirely from committing the anchor to Git**, where a pushed, distributed history is a second write boundary a local filesystem write cannot reach. What ships here is that the Git-based practice becomes automatic, ergonomic, and checked by default instead of a manual `audit head` nobody ran. `cr` writes no `.gitignore` and nothing in the repository excludes the file; `tests/audit_anchor.rs::the_anchor_is_tracked_by_git_and_excluded_by_nothing` checks that against real Git.
  Stale is separated from tampered by *position*, not by comparing head hashes. The anchor names a sequence as well as a hash, and the journal is append-only, so the event at that sequence is fixed forever: recomputing the anchor the journal implies at exactly that sequence gives "the journal is shorter than the anchor claims", "the journal has a different event there", and "the journal has the same event there and more after it" as three separable answers. Only the first two fail, as `DomainError::AnchorMismatch` / `409 anchor_mismatch`, distinct from a corrupt chain. A new variant rather than a `Conflict` for the same reason `ApprovalMismatch` is one: the *status* follows the established precedent for unusable stored state — 409, exactly as `paths::refuse_entry` and the record-name refusals map — but the machine-readable code has to separate "the chain is damaged" from "the chain is intact and is not the one your anchor attests to", because those two send an auditor to different places. The third is a pass with a notice, which is what a crash between the segment write and the anchor write legitimately leaves. A lagging anchor is a real reduction — the events past its sequence are pinned by nothing again — and `check` reports it at warning severity rather than hiding it.
  Left open on purpose: an absent anchor passes with a notice rather than failing, so deleting the file downgrades a database to the pre-anchor situation silently as far as the exit status goes, and only the notice, the `audit_anchor_missing` finding, and the Git deletion say so. `cr status` still reports `Clean` on a database whose head was forged, because `status` is the working-tree view and reads no anchor. And the anchor is not signed, which is the separate P1 entry above.

Non-string keys are pinned there as they are, not endorsed; see the entry below. `tests/query_properties.rs` covers field paths (split on every dot, no escapes, so the written form is the parts joined), `KEY=YAML` totality and exact values, `--where-expr` splitting and meaning against a reference evaluator, `--filter` by printing generated trees with arbitrary keyword case, quoting, spacing, and redundant parentheses and evaluating them beside a reference evaluator on generated records (and agreeing with `--where-expr` on shared operators), sort keys round tripping alone and in lists with the five-key and repeated-field refusals, `compare_yaml_values` as a total order, sorting as one order whatever the input order, and projections round tripping with one-line rows. `tests/http_properties.rs` sends generated requests through the in-process router — every route, awkward and broken percent-encoding, route-aware and stray query parameters, attribution, `If-Match`, `Idempotency-Key`, cookie, and content-type headers, and valid, truncated, deeply nested, mistyped, and out-of-range JSON and form bodies — to a fresh fixture per seed, and requires no `5xx` (bar a not-ready `/ready`), the error envelope with the response's own request ID on every JSON refusal, no response naming the database directory, no write from a refusal or a `GET`, and a verifying journal. It also installs generated collection schemas and requires `/openapi.json` to parse, every `$ref` to resolve (inside the nearest `$id` resource, as JSON Schema resolves it), parameters to be unique and to match each path template, operation IDs to be unique, and `x-cr-collection-schemas` to map each collection to exactly its schema; that check, and the reference check `tests/server_api.rs` had, now live in `tests/common/openapi.rs`.
  Six bugs were found and fixed, each with a regression test named for its input. A filter of a thousand `(` or `NOT` overflowed the parser's stack, which aborts the process — for `cr serve`, every connection — so nesting is bounded at 64 (`MAX_FILTER_DEPTH`). Front matter nested 121 levels deep was written with an audit event too deep for serde_json to read back, after which every read, write, and verification of the database failed; `Database::validate`, which every write calls, bounds it at 64 (`MAX_FRONT_MATTER_DEPTH`). `compare_yaml_values` called NaN equal to every number, which with the ID tie-break made a cycle, so `value: .nan` sorted differently for different input orders and panicked `slice::sort_by` with two hundred records; NaN now sorts after every number. The YAML emitter ends a block scalar whose last break is U+2028 or U+2029 with that character, so `render` glued the closing delimiter to it and the write failed unclassified with `500`; `render` now ends the line, re-parses what it wrote, and refuses as invalid anything that would not read back exactly. A collection, record, or view name longer than a directory entry, or holding a NUL, failed in the filesystem unclassified with `500`; `src/paths.rs` classifies a name the filesystem cannot store as invalid wherever it surfaces. And a path segment that was not UTF-8 once decoded got axum's plain-text `400`; every handler now extracts path parameters through `Segments`, which answers `400 invalid_path` in the envelope.
  One more was pinned rather than fixed, because the fix is a design choice: a collection schema that uses `#/$defs/...` without an `$id` embeds into the OpenAPI document with references that do not resolve there (the entry below). No `cargo fuzz` targets were added: the parser most worth coverage-guided fuzzing is the private front matter one, a `fuzz/` crate would carry its own lockfile and a nightly toolchain that CI does not build, and the seeded properties at a raised `CR_PROPERTY_SCALE` are the local deep search.

- [ ] **P2 — Resolve collection schemas' local references inside the OpenAPI document.**
  A collection schema that uses `#/$defs/...` and has no `$id` is embedded verbatim under `components.schemas`, where OpenAPI 3.1 resolves the fragment against the whole document, which has no `$defs`, so any tool that follows the reference fails. `cr` itself compiles and enforces the schema correctly, since it resolves against the schema alone. Either rebase local references onto the component's location when embedding, or give an embedded schema without one an `$id`, and decide which keeps `x-cr-collection-schemas` pointing at the schema the collection installed. `tests/http_properties.rs::a_collection_schema_with_local_definitions_resolves_inside_the_openapi_document` is ignored until then, and the generated-schema property only uses `$defs` beside an `$id`.

- [ ] **P2 — Decide what non-string front matter keys mean.**
  YAML keys can be integers, booleans, floats, null, sequences, mappings, or tagged values, and JSON — the audit journal's and the API's representation — has only strings. Integer, boolean, and float keys are stored and become their text in JSON, so `1: a` and `'1': b` are two YAML keys and one JSON key, where the later wins, and a record keyed `1` comes back from an audited state keyed `"1"`. Null and sequence keys are refused as not representable for auditing. Mapping and tagged keys fail inside the YAML emitter with an unclassified error, which only the library API can reach: the CLI's assignments and the API's JSON cannot express them, and a direct edit holding one is refused at `save`. `src/frontmatter/properties.rs::non_string_keys_are_pinned_at_the_json_boundary` and `tests/frontmatter_properties.rs` pin all of it. Either refuse non-string keys at every write, or define the stringification, refuse the collisions it creates, and classify the emitter's failure.

- [ ] **P3 — Store strings the YAML emitter cannot write exactly.**
  A string holding a line or paragraph separator (U+2028, U+2029) beside other line breaks, such as `"a\n\n "`, is written by `yaml_serde`'s emitter as a block scalar that reads back as a different string, so `Document::render` refuses it as invalid input rather than storing it changed. A single trailing separator after a line break is fine since the emitter's missing final newline is supplied. Storing the rest needs the emitter to double-quote any string with those characters, upstream or by rendering such scalars in `cr`.

- [ ] **P1 — Crash/fault injection.**
  Exercise failures at every durable-write boundary, including server termination during mutation, segment rotation, direct-edit save, and future multi-record work.
  The single-record audit write-ahead protocol is done. `tests/audit_fault_injection.rs` enumerates the four points in a mutation — pending written, record replaced, event appended, pending cleared — and proves each one recovers to the correct atomic state, for create, update, delete, and the degenerate case where the before-state and after-state are identical. Every state that is none of those four produces a named refusal that is asserted by wording: a record matching neither state, a committed event whose record was rolled back, a pending file that cannot extend the head, and one older than the committed head. `tests/audit_corruption.rs` does the same for torn and tampered state: truncated tails, a tear terminated by a newline, flipped bytes in a payload and in a stored hash, empty segments, re-hashed forgeries, unsupported versions, reordered/removed/duplicated events, segment gaps, misnamed segments, and eight malformed shapes of `pending.json`.
  The interruption is produced by blocking the name the next segment will take, so a real `cr` process writes its real pending file and its real record and then fails to append. That is deterministic and needs no hook in production code; the cost is that no test kills a process *inside* the mutation window, because there is no rendezvous that would make the kill point deterministic without such a hook. `tests/concurrency.rs` does kill a real `cr` process outright, via a sync adapter that signals its own parent, and covers writers racing recovery and writers contending for the audit lock.
  The server's shutdown path is covered by `tests/server_shutdown.rs`: neither signal `cr serve` handles can stop a mutation inside the window, a create waiting for the audit lock commits even when a second signal abandons its response, and a restarted server recovers a mutation it left half done.
  What remains: a `SIGKILL` of the HTTP server inside the mutation window, which has the same missing rendezvous as the CLI kill above, though the states it would leave are the ones already covered; the sync run ledger under `.cr/sync/runs/`, which is a separate durability mechanism and is not hash-chained; and multi-record work when it exists.

- [ ] **P2 — Larger scale and performance baselines.**
  Measure list, search, audit pagination, startup, and OpenAPI generation across realistic record counts and body sizes before designing indexes.
  The server's per-request journal walks are done. `cr serve` keeps one verified walk and extends it with appended events (`JournalCache` in `src/audit.rs`), the view index replays the journal once for every collection rather than once per collection, and `ViewIndex::summarize` pins that count in a unit test. On 5,000 records and 15,000 events across 20 collections the index went from 8.2 s to about 0.1 s warm, and a view page from 0.6 s to about 10 ms.
  The CLI's per-command journal walks are done too. Every read of a plaintext collection replayed the whole chain to check encrypted-storage ownership, and `--as` replayed it again for its own check, so one `cr get` cost time in proportion to every write ever made: about 1.5 s of CPU at 2,300 events and 10.5 MB on a small VM, twice that with `--as`, and worse again on the musl build, whose allocator maps and unmaps pages for the YAML parse of every event snapshot. Each command that appends now saves its verified walk in `.cr/cache/verified-journal.json`, the next command resumes it and verifies only what was appended since, and one process shares one walk. On the musl build with 2,300 events in 6.5 MB, `get` and `list` went from about 305 ms to 6–7 ms and `update` from 897 ms to 466 ms, and on 1,000 events `--as` went from 269 ms, twice a plain read, to 7 ms; `--verify-audit` restores one full walk per command. `src/audit.rs` and `tests/journal_cache_cli.rs` cover resumption, damaged and forged files, rewritten segments, and that a read writes nothing.
  Writes walk the chain once rather than twice. A single-record write walked it from the first event to prepare its event and again immediately before appending, and with `--verify-audit` or no cache attached the audited state it read before preparing — whether the record once owned encrypted storage, a link target's audited version, whether a user's ID was deleted — cost further walks, so on 2,300 events a release build's `update` took about 470 ms against 230 ms for one walk, and `--verify-audit update` 690 ms. Now the write walks once under the audit lock (`Admission` in `src/audit.rs`), reads that state from the walk, prepares against it, and carries it to the append, which checks the journal on disk against it as a cached walk is checked — sealed segments by identity and times, the newest byte for byte, anything appended verified — and walks from the first event again only if something already verified has changed, relying on the held lock as bulk `save` always has. On 2,300 events `update` went to about 240 ms and `--verify-audit update` to about 250 ms; on 1,000, from about 230 ms to 130 ms and from 330 ms to 120 ms, beside about 100 ms for one walk. Writes still cost one walk in proportion to history, by design. `src/audit.rs` pins one walk for `create`, `update`, `link`, `unlink`, and `delete` with no cache, a server's cache, `--verify-audit`, and a saved walk, and for registering, deleting, and refusing to reuse a user; and it refuses the append when a sealed segment is rewritten in place, the newest segment is altered, or another writer appends between the walk and the append.
  Writes resume the saved walk too, so they no longer cost time in proportion to history. A write verifies the events appended since the walk the last write saved, prepares and appends against it, and saves it; each walk records how long the journal was when it, or the walk it descends from, last verified every event from the first, and once `audit.full_walk_after_events` (64 by default) have been appended since, the next write walks from the first event. On a release build, 64 consecutive `update`s took a median of 23 ms on both 1,000 and 2,300 events, against 122 ms and 244 ms, and a mean of about 30 ms including the one full walk. The trade is the saved walk's: a forged one steers writes until that full walk, which refuses the journal at the first event built on it, as `cr audit verify` does; `--verify-audit` or `full_walk_after_events: 1` restores a walk from the first event per write. `src/audit.rs` pins the one-in-N cadence, refuses a resumed write over a rewritten segment, and executes the forged-walk bound.
  What remains: the full walk itself is still linear, so the one write in N that makes it is as slow as every write used to be, and the walks `audit verify`, `check`, and `--verify-audit` make are unchanged. An HTTP write with an `Idempotency-Key` walks the chain once more to look up an earlier result, because the walk keeps idempotency identities but not their results; access-management writes (`cr access`, user updates) check the principal's audited policy before their walk, which with no cache or `--verify-audit` is a walk of its own; `audit baseline` walks once per record it baselines rather than once, as `save` does; a preview with no cache attached walks again to reveal its result; and pending recovery walks twice, as it always has. History pages now share an in-memory index of verified event offsets and exact encryption transitions, so task history and audit pagination no longer replay the whole chain on every request. The first history read after resuming a saved walk still establishes that index with one full replay. Schema validation is cached by exact file contents, and Kanban move permissions are checked only for displayed cards. Every page still reads and parses each record it lists, and record pages scan readable collections for relations; indexes for materialized records and relations would remove that remaining work.

- [ ] **P2 — Find why sync recovery on macOS can overwrite a target changed after its history scan.**
  `tests/sync_cli.rs::recovery_cannot_overwrite_a_target_changed_after_its_history_scan` pauses `cr sync recover` between audited mutations (SIGSTOP once the audit lock is free, after record `p020`), updates `notes/guard` twice from another process so its content, and so its version, ends where it started while the audit generation moves on, then resumes the recovery and expects it to refuse to write `guard` with "changed since the expected audit generation". On `macos-latest` the recovery sometimes succeeded instead: on `main` after #88 and #90 and on PR #94, all UI-only changes, and each passed on rerun. It has not failed on Linux. Whether the guard misses the change or the test's pause lands somewhere it did not intend, a stale recovery overwriting a newer local write is the failure the guard exists to prevent, so reproduce it on macOS in a loop and find which before changing either. CI stopped running the test suite on macOS on 2026-09-24 because of this failure, so it can only be found on a Mac now.

- [ ] **P2 — Find why concurrent first writes on macOS can fail to open the audit lock.**
  `tests/idempotency.rs::concurrent_cli_retries_commit_one_event_and_all_return_success` starts eight `cr create` processes against a database no write has touched yet. Once on `macos-latest` (PR #60, passing on rerun) one of them failed with `could not open the audit lock at …/.cr/audit/lock: No such file or directory`. `paths::open_lock_file` opens the lock with `openat(O_RDWR | O_CREAT)` relative to a descriptor for `.cr/audit` that `create_directory_all` has just opened or created, and nothing in `cr` removes or renames that directory, so `ENOENT` should be impossible there; it has not reproduced on Linux. Reproduce it on macOS in a loop before changing anything. A bounded retry of the open on `ENOENT` would hide the symptom, but only a confirmed cause justifies it, because the same error from a genuinely removed directory must still fail.
